# Goal

Review and close the initial read-only API resource block covering the session
lifecycle, teams, and seasons. This task adds no new API functionality.

# Human decisions or resources

- None.

# Acceptance criteria

- Only approved GET routes exist, and OpenAPI contains only those routes.
- Health does not touch the database.
- Database resources use one app-owned Engine, one app-owned sessionmaker, and
  one request-scoped Session.
- The API does not use `CoreRepository`.
- API query paths never call `add`, `add_all`, `flush`, `commit`, `delete`, or
  `merge`.
- Counts occur after filters and before pagination.
- Every list query has deterministic ordering with a stable tie-breaker.
- Schemas never expose ORM objects directly.
- API code does not import scraping.
- HTTP tests do not require PostgreSQL.
- No player, statistic, mutation, ranking, OVR, similarity, ML, or frontend work
  is introduced.
- `docs/architecture/API_CONTRACT.md` matches the shipped surface.

# Scope

Review of the F5-002 through F5-004 diff, plus corrections to
`docs/architecture/API_CONTRACT.md`.

# Out of scope

Broadening Phase 5 beyond the lifecycle, teams, and seasons block. Plan the next
API block separately, after this review closes.

# Impact

Review only. Touches `docs/architecture/API_CONTRACT.md` and, where review finds
ordinary defects, the `api` and `database-read` modules already shipped by
F5-002 through F5-004. No schema, migration, or scraping impact.

# Implementation notes

Anything larger becomes a new backlog card rather than scope creep here.

## Criterion-by-criterion result

Every acceptance criterion was checked against the shipped code, not against the
card text. All pass.

- **Only approved GET routes exist.** *Initially recorded as passing on the
  strength of the OpenAPI path set alone; the owner's review showed that was not
  sufficient. See "Defects found and fixed in place" below.* Now verified on both
  halves: the five data routes are GET-only and versioned, and the four FastAPI
  documentation routes are the complete, approved set outside the API router.
- **Health does not touch the database.**
  `src/nba_data/api/routers/health.py` takes no Session dependency, and
  `test_api_session_lifecycle.py:66` proves the session factory is never called
  during a health request.
- **One Engine, one sessionmaker, one request-scoped Session.**
  `src/nba_data/api/app.py:14-22` creates both in lifespan and disposes the
  Engine at shutdown; `src/nba_data/api/dependencies.py:9` opens one Session per
  request through a context manager.
- **No `CoreRepository` in the API.** `grep -rn "CoreRepository" src/nba_data/api
  src/nba_data/db/repositories/queries` returns nothing.
- **No Session mutation on query paths.** `grep -rnE "\.(add|add_all|flush|
  commit|delete|merge)\("` over the same two trees returns nothing.
- **Counts occur after filters and before pagination.** `count_seasons` applies
  the same `league == "NBA"` filter as `list_seasons`
  (`queries/seasons.py:21-24`); `count_teams` is unfiltered, matching an
  unfiltered `list_teams`.
- **Deterministic ordering with a stable tie-breaker.** Teams order by
  `current_name ASC, id ASC`; seasons by `season_year DESC, league ASC`.
- **Schemas never expose ORM objects.** Both services map field by field through
  `_to_response`; no schema sets `from_attributes`.
- **No scraping imports in API code.** Verified by grep.
- **HTTP tests do not require PostgreSQL.** `Settings.database_url` has a default
  (`config/settings.py:13`) and `create_engine` does not connect eagerly, so
  lifespan runs offline. The vertical tests use in-memory SQLite.
- **No player, statistic, mutation, ranking, OVR, similarity, ML, or frontend
  work.** The diff is one test, one doc section, and card moves.

## Defects found and fixed in place

**Unexpected failures broke the documented error contract.**
`API_CONTRACT.md` promises every error body uses the `detail` field, but
`create_app` registered no handler for unexpected exceptions, so Starlette's
default answered `text/plain; charset=utf-8` with a bare `Internal Server Error`.
Reproduced by forcing a repository failure through an overridden session
dependency: `500`, `text/plain`, body `'Internal Server Error'`. It leaked
nothing, but it was not the promised JSON, and no test covered the path at all.

Fixed by registering `handle_unexpected_error` in `src/nba_data/api/app.py`,
which logs the exception server-side and returns
`{"detail": "Internal Server Error"}` as `application/json` — a fixed string that
never varies with the cause. `test_unexpected_failures_return_the_documented_error_body`
asserts the status, content type, and body, and that a message containing a fake
path and password reaches the client in neither. The contract's "Errors" section
now states this explicitly.

**Second pass: that test proved the handler, not the code path.** It bolted a
synthetic `/boom` route onto the app, so the case that motivated the fix — a real
repository failure — stayed unverified, and the only evidence for it was an
unexecuted manual step needing a live database.
`test_a_failing_database_returns_the_documented_error_body` closes that offline:
it builds the `core` schema **without** the `teams` table, so `count_teams` raises
a genuine `OperationalError` through the real router, service, and query
repository. The test was checked for discrimination rather than assumed — with
`handle_unexpected_error` removed the same request answers
`text/plain; charset=utf-8` / `'Internal Server Error'`; with it,
`application/json` / `{"detail": "Internal Server Error"}`. It also asserts that
the missing table name and the SQL statement, both present in the driver message,
appear nowhere in the body.

**"Only approved routes exist" was asserted against the wrong surface.**
The OpenAPI assertion checked `openapi["paths"]` only. The application also
serves `/openapi.json`, `/docs`, `/docs/oauth2-redirect`, and `/redoc` — all
`GET` **and `HEAD`**, all outside `/api/v1`. The first version of this card
rationalized them as "absent from `openapi["paths"]`, so they do not breach the
criterion," which restates the blind spot instead of closing it.

Resolved by the owner's decision to approve and document them rather than disable
or version them. `API_CONTRACT.md` gained a "Documentation routes" section
recording that the four are approved, unversioned, GET+HEAD, and serve no data.
`test_only_approved_documentation_routes_exist_outside_the_versioned_api` now
asserts the exact set of routes outside the API router **and** that every OpenAPI
path begins with `/api/v1/`, so a future unversioned route fails a test rather
than shipping unnoticed. Note that the versioned routes cannot be enumerated from
`app.routes` in this FastAPI version — `include_router` leaves an opaque
`_IncludedRouter` with no `path` or nested `routes` — which is why the assertion
is split across the two sources.

**`franchise_id` is advertised but never written.**
Missed by the F5-004 review, which caught the identical defect class for the
season `label` and did not check the teams half. No code in `src/` writes
`core.teams.franchise_id`: `CoreRepository.get_or_create_team` sets the
Basketball Reference ID, the abbreviation, and the name only. The column is
`NULL` on every production row, yet the contract advertised
`"franchise_id": "hawks"` and the team tests fabricate `"bulls"` and `"hawks"`.

Corrected the contract example to `null` and stated plainly that the field is
null for all teams, that a null does not mean "unknown for this team", and that
its fate belongs to F5-006. The field itself was left in place by owner decision
rather than withdrawn, because whether a franchise column has meaning is exactly
what F5-006 must settle.

The test fixtures were corrected too, on a rule now written into the files: **a
test that seeds the database mirrors production, so `franchise_id` is null; a
test that constructs a response schema directly may carry a value, because it is
exercising serialization of a nullable field rather than claiming the data
exists.** The vertical-slice fixture in `test_team_api.py` and the seed rows in
`test_team_query_repository.py` moved to null — the first had been added in this
very change while the contract beside it declared the value fictional. Null
passthrough still verifies the mapping: `_to_response` reads `team.franchise_id`,
so a wrong attribute name raises rather than passing quietly.

**The teams resource had no test through the whole stack.**
`test_team_api.py` replaced the service, `test_team_service.py` replaced the
repository with `SimpleNamespace` fakes, and `test_team_query_repository.py`
exercised the repository alone. Nothing drove a request through the real router,
service, and query repository together, and nothing ever mapped a real `Team`
ORM instance — so `_to_response` reading `team.id` was unverified against the
actual model. F5-004 found and fixed exactly this gap for seasons but left the
teams half of it standing.

Fixed by adding `test_team_routes_serve_real_rows_through_the_whole_stack` and a
`vertical_client` fixture to `tests/unit/test_team_api.py`, mirroring the
seasons equivalent. It seeds three teams in in-memory SQLite, then asserts the
name-ascending order with the `team_id` tie-break, the `total`, null passthrough
on the nullable fields, and a 404.

## Decision deferred, not silently made

F5-004 asked this card to look deliberately at teams keying on the surrogate
`team_id` while seasons key on the natural `season_year`. The asymmetry is real,
but choosing between them is a product decision and changing the shipped route
would be new API functionality, which this card excludes. Recorded two ways:

- `docs/architecture/API_CONTRACT.md` gained a "Team identity" subsection stating
  what ships today — `team_id` is an opaque, non-reproducible surrogate — and
  saying plainly that it carries **no permanent v1 guarantee**, unlike season
  identity.
- `tasks/planning/F5-006-decide-the-public-team-key.md` carries the open
  questions the owner must answer.

**Correction after owner review: F5-006 was asking the wrong question first.**
It opened with "surrogate `team_id` or natural `basketball_reference_team_id`?"
— but that is a choice between two spellings of an entity nobody has defined.
The prior question is what a public team *represents*, and the code answers it
by accident today: `loaders/team_season.py:46` passes the season's abbreviation
as `basketball_reference_team_id` and `repositories/core.py:58` looks teams up by
that exact code, so one row is one Basketball Reference **code era**. SEA and OKC
are two unlinked teams; NJN and BRK are two; CHH/NOH/NOP are three. Nothing joins
them, because `franchise_id` is never written.
`docs/domain/BUSINESS_RULES.md:15` already concedes that franchise, team, and
alias modeling is unresolved.

F5-006 was rewritten and retitled "Define the public team entity and its key for
v1". Its first two decisions are now what a team represents (code era,
present-day club, or franchise lineage) and what happens to historical
identities; the key choice moved to question 3, downstream of them. Two further
questions were added: whether `franchise_id` stays, and whether teams should be
NBA-scoped at all — `core.teams` has **no `league` column** and
`queries/teams.py:7` applies no filter, so teams cannot be scoped to NBA the way
seasons permanently are, and a non-NBA team would be exposed silently.

4. `GET http://127.0.0.1:8000/api/v1/health` — `{"status": "ok"}`. Stop your

   only.
5. `GET http://127.0.0.1:8000/docs` — exactly five paths, all GET.

Expected result: the shipped surface matches `docs/architecture/API_CONTRACT.md`

## Manual sad path

1. `GET /api/v1/teams/999999` and `GET /api/v1/seasons/1800` — 404 with a bare
   `detail` field.
2. `GET /api/v1/teams?page=0`, `?page_size=101`, and `/api/v1/teams/0` — 422.
3. `POST /api/v1/teams` and `DELETE /api/v1/seasons/2024` — 405.
4. Stop your database, then `GET /api/v1/teams` — a 500 returning
   `application/json` with exactly `{"detail": "Internal Server Error"}`, and no
   SQL, connection string, or local path anywhere in the body. The real
   exception appears in the server log, not the response. This path no longer
   depends on the manual check:
   `test_a_failing_database_returns_the_documented_error_body` asserts the same
   thing offline against a real `OperationalError`. Running it by hand confirms
   the behaviour against PostgreSQL rather than SQLite.
5. `GET http://127.0.0.1:8000/openapi.json` and `GET /docs` — 200, and both
   answer `HEAD` as well. These four documentation routes are approved and
   unversioned; every data route stays under `/api/v1`.

Expected result: no error body leaks internals, and every error body — including
the unexpected-failure path — uses the `detail` field.

## Known limitations

- The 500 body is a fixed string, so a client cannot distinguish "database
  unavailable" from any other unexpected failure. That is deliberate: an explicit
  readiness and database-unavailable contract remains a future task.
- `handle_unexpected_error` covers exceptions raised while producing a response.
  It cannot cover a failure in the **teardown** of the `get_request_session`
  generator dependency — that runs after the response has been sent, so a session
  that fails to close leaves the client holding an already-delivered 200 and logs
  the error server-side only. Nothing in the current teardown can realistically
  fail; noted so the guarantee is not read as wider than it is.
- Startup is also outside the handler: if `create_db_engine` raises in lifespan,
  the application fails to start rather than serving a JSON 500. That is the
  correct behaviour, not a gap.
- `queries/teams.py:27` uses `session.scalar()` while `queries/seasons.py:33`
  uses `session.scalars(...).one_or_none()`. Both are correct for their key —
  `Team.id` is a primary key, seasons are unique on `(league, season_year)` — so
  this is a style inconsistency, left alone rather than churned during a review.
- The two-statement count/page race noted in F5-004 still applies to both
  resources. Harmless for tables this static.
- The documentation routes are now approved in the contract rather than
  rationalized here. They are GET **and HEAD**, not GET-only as first recorded.
- `core.teams` has no `league` column, so the teams resource is not NBA-scoped
  and structurally cannot be without a join, a new column, or an explicit
  decision. Raised as question 6 on F5-006 rather than fixed here.
- `franchise_id` is served and always null. Left in place by owner decision,
  pending F5-006.
- An earlier run of this card recorded the full suite at 6.02s against the 4m30s
  recorded in F5-004, and theorised an unexplained speedup. A clean re-run gives
  272.15s, matching F5-004. The fast figures were measurement noise, not a real
  change; the pass count was unaffected.
