# Goal

Expose the first read-only season resources: `GET /api/v1/seasons` and
`GET /api/v1/seasons/{season_year}`, using a dedicated read-only query
repository, explicit Pydantic schemas, a service layer, and an HTTP router.

# Human decisions or resources

- None.

# Acceptance criteria

- Only the two GET routes are added.
- The repository receives an existing Session and never creates, closes, commits,
  flushes, mutates, or returns a Session.
- The API does not use `CoreRepository`.
- Responses expose only the fields below and never serialize ORM objects
  directly.
- The internal season ID is never exposed.
- Missing seasons return 404; invalid path or pagination inputs return 422.
- Valid empty pages return 200 with `items: []`.
- Repository, service, HTTP, and OpenAPI tests are offline and deterministic.

# Scope

`src/nba_data/api/app.py`, `src/nba_data/api/routers/seasons.py`,
`src/nba_data/api/schemas/seasons.py`, `src/nba_data/api/services/seasons.py`,
`src/nba_data/db/repositories/queries/seasons.py`, the three matching unit test
modules, and `docs/architecture/API_CONTRACT.md`.

# Out of scope

The internal season ID, public multi-league support, players, teams-by-season,
statistics, write routes, model changes, migrations, scraping, live database
requirements.

# Impact

Adds one router, one schema module, one service, and one query repository to the
`api` flow in `docs/architecture/IMPACT_MAP.md`. Reads `core.seasons` only — no
schema change, no migration. Extends `docs/architecture/API_CONTRACT.md` and the
OpenAPI surface asserted by the API tests.

# Implementation notes

Public season contract:

- `season_year: int` — the public identifier; `2024` means the 2023-24 season
- `league: str`
- `label: str | null`

Initial scope is NBA only, `league = "NBA"`. Order by
`season_year DESC, league ASC`.

Follow the layering established by F5-003 (teams), which is present in this
branch: `src/nba_data/api/{routers,schemas,services}/teams.py` and
`src/nba_data/db/repositories/queries/teams.py` are the reference
implementation. The `queries/` package already exists — add `seasons.py` to it
rather than recreating it.

## Manual happy path

1. Start the API against your local dev database:
   `uv run uvicorn nba_data.api:create_app --factory`
2. `GET http://127.0.0.1:8000/api/v1/seasons` — the collection envelope with
   `page: 1`, `page_size: 50`, `total` equal to the number of NBA seasons, and
   `items` ordered by `season_year` descending.
3. `GET http://127.0.0.1:8000/api/v1/seasons/2024` — the single season. `label`
   reads `"2024"`, not `"2023-24"`; the loader stores the year as a string.
4. `GET http://127.0.0.1:8000/docs` — only `/api/v1/seasons` and
   `/api/v1/seasons/{season_year}` are added, both GET-only.

Expected result: every season object has exactly `season_year`, `league`, and
`label`. No internal season ID appears anywhere in the payloads or in the
OpenAPI schema.

## Manual sad path

1. `GET /api/v1/seasons/1800` — 404 with `{"detail": "Season not found"}`.
2. `GET /api/v1/seasons/not-an-integer` and `GET /api/v1/seasons/0` — 422.
3. `GET /api/v1/seasons?page=0` and `GET /api/v1/seasons?page_size=101` — 422.
4. `POST /api/v1/seasons` and `DELETE /api/v1/seasons/2024` — 405.
5. `GET /api/v1/seasons?page=999` — 200 with `items: []` and the real `total`.

Expected result: error bodies use the standard `detail` field only, with no SQL,
connection string, or local path in any response.

## Corrections made during review

- **`label` format.** The contract and the new test fixtures originally showed
  `"2023-24"`. The only writer of a season row is
  `CoreRepository.get_or_create_season`, which sets `label=str(season_year)`, so a
  real label is `"2024"`. The contract example, its description, and all three
  test modules were corrected to match what the loader actually produces.
- **Untested HTTP-to-SQL seam.** The API tests replaced the service and the
  service tests replaced the query repository, so no test drove a request through
  the real router, service, and repository together, and nothing ever mapped a
  real `Season` ORM instance. `test_season_api.py` gained
  `test_season_routes_serve_real_rows_through_the_whole_stack`, which serves a
  request from a seeded in-memory SQLite session with only the lifespan engine
  faked. It needs `check_same_thread=False` because sync routes run in the
  threadpool.
- **Season identity decided, not deferred.** `core.seasons` is unique on
  `(league, season_year)`, so `season_year` alone is a valid key only inside a
  fixed league. The owner decided v1 pins that league to NBA permanently, and
  `API_CONTRACT.md` now states it explicitly, including that resources built on
  seasons inherit the scope and must not reintroduce league within v1.

## Known limitations

- Both routes are pinned to `league = "NBA"`: `total` counts NBA seasons only,
  and a `season_year` that exists only in another league returns 404. This is now
  a deliberate, documented v1 guarantee rather than a temporary scope note. No
  code in `src/` writes a non-NBA league today, so the filter removes nothing in
  practice and `league` is effectively a constant field.
- The teams resource keys on the internal surrogate `team_id` while seasons keys
  on the natural `season_year`. Both are now shipped in v1, so composite routes
  will mix the two styles. Worth a deliberate look in F5-005.
- `count_seasons` and the page query are two statements, so a concurrent backfill
  can make `total` disagree with `items`. Harmless for a table this static.
- `tests/unit/test_api_foundation.py` was edited outside the card's stated scope:
  it asserts the exact OpenAPI path set, so registering the router required
  adding the two seasons paths there. No other change to that file.
- `docs/architecture/API_CONTRACT.md` now documents the shipped teams resource as
  well, correcting the stale "Planned resources" entry F5-003 left for F5-005.
