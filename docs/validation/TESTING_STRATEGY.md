# Testing Strategy

## Offline suite

The unit-test lane is deliberately independent of PostgreSQL and network
access. It runs Ruff, Mypy, and Pytest, in that order:

```bash
uv run ruff check .
uv run mypy src/nba_data
uv run pytest -m "not integration and not live"
```

Mypy is a gate, not advice: CI fails on any error it reports. Its scope is
`src/nba_data` only — `tests/`, `scripts/`, `alembic/` and the legacy prototype
are excluded, and the path is spelled out in CI and in the README so that scope
is visible rather than implied by the working directory. It enforces the
`[tool.mypy]` settings in `pyproject.toml` as they stand; raising that bar
(`strict`, `disallow_untyped_defs`) is a separate decision.

Normal unit and offline validation never needs PostgreSQL, and nothing in that
lane opens a database connection.

The full local `uv run pytest` command still *collects* the integration
directory. Without the authorization described below, its database-dependent
tests skip before any Engine is built, and no live scraping or Basketball
Reference request is made.

## PostgreSQL integration lane

This is the authoritative description of the lane. `tests/integration/conftest.py`
implements all of it; individual test modules own assertions and nothing else.

### Authorization: two environment variables

| Variable | Accepted values | Meaning |
|---|---|---|
| `NBA_DATA_TEST_DATABASE` | exactly `1` after trimming | The database named by `DATABASE_URL` is disposable and may be written to. |
| `NBA_DATA_REQUIRE_POSTGRES_INTEGRATION` | `1`, `true`, `yes`, `on`, any case | Required mode: environment problems fail instead of skipping. |

The two rules differ on purpose. `NBA_DATA_TEST_DATABASE` is a fail-closed
safety interlock, so only the exact value `1` counts — a typo must not read as
consent. `NBA_DATA_REQUIRE_POSTGRES_INTEGRATION` cannot cause a write on its
own and keeps the repository's ordinary truthy convention.

Neither belongs in `Settings`. Application code has no business knowing whether
a database has been volunteered for destruction.

### The database name must also be disposable

Beyond the flag, the database parsed from `DATABASE_URL` must be exactly
`nba_test_ci` (the CI service container) or begin with `nba_test_tmp_` (a
scratch database generated by the local validator). Setting the flag while
pointing at any other database is a dangerous configuration error, and it
**fails in both modes, before connecting** — it is not skipped past.

### What happens before a connection is opened

In order, and entirely on environment variables and a parsed URL:

1. Read required mode.
2. Check `NBA_DATA_TEST_DATABASE`; skip locally, fail in required mode, naming
   the flag either way.
3. Parse `DATABASE_URL`, require the PostgreSQL backend, and require an
   approved database name.

Only then is an Engine constructed, `SELECT 1` issued, `alembic_version` read,
and the applied revisions compared against the repository's Alembic heads —
which are resolved dynamically from the shipped migration scripts, never from a
hard-coded list. A whitelist of revisions is a test that fails every time a
migration lands, which is exactly how this lane broke once.

### Skip versus fail

| Condition | Local | Required mode |
|---|---|---|
| Safety flag absent or malformed | skip before connecting | fail before connecting |
| PostgreSQL unavailable | skip | fail |
| `alembic_version` missing or empty | skip | fail |
| Schema behind or ahead of the repository heads | skip | fail |
| Flag set plus an unapproved database name | **fail** before connecting | **fail** before connecting |

Only environment conditions are eligible. An assertion made by a test is never
converted into a skip. "Zero skips" is not a general policy; these specific
conditions are simply not skippable where it matters.

### Isolation

- Every database-mutating test receives a function-scoped `Connection` inside
  one explicit outer transaction, rolled back unconditionally in teardown. No
  test commits it.
- Sessions are bound to that Connection with
  `join_transaction_mode="create_savepoint"`, so a `Session.commit()` by the
  code under test releases a savepoint rather than committing the fixture's
  transaction. The loader keeps its real caller-owned-transaction contract.
- API tests seed rows through the same Connection and never commit them. Each
  HTTP request receives a **fresh** Session, created inside the
  `get_request_session` override and closed when the request ends, joined to
  that Connection by savepoint. Every database route resolves its Session
  through that one dependency, so teams, seasons, and readiness are all covered.
  No Session crosses a thread boundary, and requests are made serially.
- Every mapped `core` table must be empty **before and after** the integration
  session. Before, it rejects a database that is evidently not disposable;
  after, it catches a test that escaped its rollback. The table list is derived
  from the mapped metadata, so a new model is covered automatically.

### Sequences do not roll back

PostgreSQL sequence values advance even inside a transaction that is rolled
back, so a test can consume ids that no surviving row uses. This is acceptable
only because every accepted database is disposable: CI destroys its service
container and the local validator drops its scratch database. Never treat a
surrogate id as evidence of cleanup or of ordering.

### The supported local command

```bash
uv run python scripts/validate_postgres_local.py
```

It creates a uniquely named `nba_test_tmp_*` database on the configured
PostgreSQL server, sets both flags for the child process only, and runs, in
order: `alembic upgrade head`, `alembic check`, `alembic downgrade -1`,
`alembic upgrade head`, `alembic check`, then `uv run pytest -ra
tests/integration` — the whole directory, so a new integration module is
included the moment it is written. Afterwards it independently verifies every
mapped `core` table is empty, and it drops the scratch database in all
outcomes. It never migrates, seeds, or drops the configured source database.

This script is a **required pre-push check** for any change to Alembic
revisions, SQLAlchemy schema or models, database loaders, or the PostgreSQL
integration fixtures and tests.

Never run `alembic upgrade head` against the developer's real database to
validate a migration; applying a migration to a persistent database is an
owner-approved operation.

`scripts/validate_database.sh` starts the local Docker PostgreSQL service and
delegates to the validator above. It creates and drops the disposable scratch
database through that validator, runs the whole integration directory, and
never migrates, seeds, or drops the configured source database.

### What a scratch-database pass does not prove

A green run against an empty disposable database proves the fresh-schema and
constraint contracts. It says nothing about whether some arbitrary populated
database is ready for a migration. `0007_team_bref_id_not_null` in particular
sets `NOT NULL` without a backfill, so before any owner-authorized application
to a persistent target, count the offending rows on that exact target first:

```sql
SELECT count(*)
FROM core.teams
WHERE basketball_reference_team_id IS NULL;
```

A non-zero result stops the migration for a separate remediation decision.

The executable preflight for this check requires the target to be named
explicitly and performs no repair or migration:

```bash
uv run python scripts/preflight_migration_data.py   --database-url postgresql+psycopg://user:password@host:5432/database
```

It takes no default and rejects an empty or non-PostgreSQL URL as a usage error
before connecting, so it cannot assess a different database from the one being
migrated. Its connection is opened read-only, which
`tests/integration/test_preflight_migration_data_postgres.py` proves by having
the server refuse a write through it; that module also runs the count itself
against the real schema, which the offline tests cannot do.

### The deliberate exception

`tests/integration/test_api_unreachable_database.py` requests none of the shared
fixtures. Its subject is a database that is not there, supplied privately
through `Settings`, so requiring the opt-in flag would make an offline-safe test
refuse to run. It executes in every configuration.

## Test rules

- Unit tests for settings defaults.
- Unit tests for HTML cache `.html.gz` read/write behavior.
- Unit tests for the rate-limited client with mocked HTTP.
- Unit tests for parser behavior with fixture HTML.

- No network calls in tests.
- No live scraping in CI.
- No Basketball Reference contact in CI.
- Use fixture HTML for parser tests.
- Use mocks for HTTP client tests.
- Use temporary directories for cache tests.

## Future tests

- DB integration tests for SQLAlchemy models and repositories.
- Data quality tests for row counts, nullability, duplicate natural keys, and
  numeric ranges.
- Manual live smoke tests for approved scraping jobs only.
